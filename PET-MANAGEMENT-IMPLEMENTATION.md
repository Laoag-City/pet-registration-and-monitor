# Pet management — September 21, 2026

Staff and admins can edit pets and remove them from active use after confirmation. Removal preserves stored pet details, medical history, photos, and historical notifications. Regular owners cannot access these management actions.

1. **Inspected:** Routes and role middleware; Pet/User/Vaccination/DewormingRecord models; actual PostgreSQL columns and foreign keys; existing edit/register forms and UpdatePetRequest; medical controllers and MedicalRecordRequest; PetCareReminders; PetQrReference and QRCodeController; staff analytics; owner/profile synchronization; existing isolated-test configuration and audit scripts.
2. **Files changed:** `app/Models/Pet.php`; `app/Http/Controllers/StaffController.php`, `VaccinationController.php`, `DewormingController.php`, `AdminController.php`, `ProfileController.php`; `app/Http/Requests/UpdateProfileRequest.php`; `app/Services/StaffDashboardAnalytics.php`; `routes/web.php`; `resources/views/staff/pets.blade.php`, `staff/edit-pet.blade.php`, `pet-details.blade.php`, `layouts/app.blade.php`; `tests/Feature/PublicQrScanTest.php`. Added `resources/views/staff/remove-pet.blade.php`, `database/migrations/2026_09_21_000000_add_deleted_at_to_pets_table.php`, `tests/Feature/PetManagementTest.php`, and this report. Existing uncommitted work was preserved.
3. **Routes:** Existing `GET /staff/pets/{pet}/edit` and `PUT /staff/pets/{pet}` remain. Added `GET /staff/pets/{pet}/remove` (`staff.pets.remove`) for confirmation only, and `DELETE /staff/pets/{pet}` (`staff.pets.destroy`) for removal. All are inside the existing authenticated staff/admin route group. The application uses this `/staff` prefix; no unprotected `/pets/{pet}/edit` alias was introduced.
4. **Controller:** Added confirmation and destroy actions. Confirmation loads the current owner and medical-record counts. Destroy requires an accepted confirmation field, locks the active pet row in a transaction, and calls the model's soft-delete operation. Successful removal redirects to All Pets with a preservation message. Existing update action continues updating the same record using validated, explicitly allowed fields.
5. **Authorization:** Existing `auth`, `auth.session`, and `role:staff,admin` middleware remain authoritative. Existing UpdatePetRequest also authorizes managers. New confirmation/destroy actions additionally check `canManageRecords()`. No submitted role or owner ID grants access. No policy framework replacement.
6. **Edit UI:** Existing form reused, with current owner and existing photo displayed. Owner information is read-only. All Pets now provides View/Edit/Remove actions; Pet Details displays Edit Pet/Remove Pet only for staff/admin. Remove opens a confirmation page, not an immediate mutation. Existing sidebar highlights All Pets on confirmation.
7. **Editable fields:** Name, species, breed, sex, birth date, color, and optional replacement photo.
8. **Protected fields:** Pet ID, code, owner identity/contact relationship, creation timestamp, deletion state, and medical relationships are outside the update whitelist. Submitted owner/identity fields already covered by UpdatePetRequest are rejected. Microchip was not added to any interface or editable field.
9. **Confirmation:** Shows pet and owner names, retained vaccination/deworming counts, and the effect on lists, QR access, and reminders. Cancel links back to Pet Details and performs no mutation. Submission requires a checked confirmation, CSRF token, and DELETE method spoofing. Missing confirmation fails validation. Missing CSRF is rejected with 419.
10. **Removal strategy:** Laravel SoftDeletes on Pet, using a nullable, indexed `deleted_at`. No public force-delete or restore endpoint was added.
11. **Why:** The actual vaccination/deworming foreign keys use ON DELETE CASCADE, and Pet previously had no soft deletion. A hard delete would erase medical history. The single additive migration preserves every existing row and foreign key. Its rollback deliberately refuses to remove archival state; future schema changes must roll forward. The migration was previewed and applied to the existing database. No reset, wipe, or destructive migration was used.
12. **Vaccinations:** Rows and foreign keys remain stored. Active lists already select through active Pet queries, so archived pets' records disappear from active medical screens. Direct edit links now return 404 when their pet is archived; existing update transactions also require an active pet. New records cannot be assigned to an archived pet through the existing ownership validation.
13. **Deworming:** Same retention, list filtering, direct-edit guard, and active-pet update behavior as vaccinations. No cascade rules were changed.
14. **QR:** Existing encrypted QR references still work after an edit because the same ID and creation timestamp remain. Resolution uses Pet's default query scope, so removed pets return the existing safe not-found page (404). Authenticated detail/download routes also exclude archived pets through route binding.
15. **Notifications:** Existing reminder selection uses active pets and `whereHas('pet')`; archived pets therefore produce no new schedules or reminders. Existing active-notification filtering hides their reminders without deleting stored notification history. Removal locks the same pet row used by medical updates/reminder generation, serializing these operations.
16. **Analytics and ownership:** Pet totals, monthly registrations, species distribution, and current schedules automatically exclude soft-deleted pets. Staff medical summary counts now count records belonging to active pets using `whereHas('pet')`. Upcoming/overdue and unique attention counts exclude archived pets. Owner/admin profile synchronization explicitly includes archived pets because ownership is email-based; changing an account email must preserve historical ownership. Accounts with archived pets remain protected from deletion. Other pages retain their existing layouts.
17. **Validation/photo:** Reused existing server rules: name 120 characters; species 60; breed 120; Male/Female sex; valid birth date no later than today; color 80; optional JPEG/PNG/WebP image up to 4096 KB. Bootstrap errors and old input remain. With no upload the existing photo path stays unchanged. A valid replacement is stored through the existing public disk. Existing files are retained, including during removal; no automatic file deletion was introduced.
18. **Tests:** All mutation tests use the existing fail-closed SQLite `:memory:` test environment. Added role-based edit/removal tests, ownership/ID/medical/QR preservation, confirmation cancellation and missing confirmation, owner denial and forged roles, invalid date/executable upload rejection, valid photo replacement, archived medical route guards, reminder suppression/history retention, active-list/dashboard exclusion, and email-based ownership preservation. Public QR test fixtures were adjusted to use unique retained legacy values because soft-deleted rows continue occupying their unique keys.

After correcting that fixture, all 15 pet-management/QR tests passed (276 assertions); the other 115 selected tests had passed. Three additional microchip-removal tests passed (82 assertions). Thus all 133 selected tests passed across their final runs. The production read-only HTTP audit passed 164 checks. Additional read-only checks returned 200 for staff/admin edit and confirmation pages, and 419 for DELETE without CSRF. Analytics checks, migration status, route listing, PHP syntax, and diff whitespace checks passed. The final real-database check showed zero archived pets; no real pet was removed for testing.
20. **Remaining limits:** Browser interaction and visual inspection were unavailable in this session; confirmation pages were verified through rendered HTTP responses and feature tests. No archive browsing or restore UI was requested or added. GD is absent in local PHP, so the valid-image test uses a small real PNG fixture instead of a GD-generated image. Existing photos and notification history remain on disk/in storage intentionally.
