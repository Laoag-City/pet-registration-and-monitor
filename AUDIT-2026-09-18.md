# PawID audit — 18 September 2026

**SYSTEM STATUS: Working with issues.** Verified defects were fixed and regression checks pass. Some requested features do not exist, and interactive browser/visual PDF checks could not be completed in this environment.

## Scope and data safety

Audited Laravel routes, middleware, controllers, models, migrations, Blade templates, frontend entry points, dependency advisories, PostgreSQL integrity, generated responses, and automated tests.

No development database migrations, resets, drops, wipes, user password changes, or domain-record deletions were performed. No PostgreSQL configuration or `.env` changes were made. All mutation tests ran against SQLite `:memory:`. The test base now refuses to boot against another database. Tests run ordinary `migrate` only against that isolated in-memory database; they do not invoke `migrate:fresh`.

PostgreSQL audit helpers use an explicit READ ONLY transaction and roll it back. The HTTP helper uses in-memory sessions/cache. Existing counts before and after: **12 users, 5 pets, 0 vaccinations, 0 deworming records**. Existing QR identifiers were preserved; QR images/PDFs are generated on demand rather than stored in a QR-record table.

### Database integrity

- Role distribution: 9 owners, 1 staff, 2 admins; no unexpected role values.
- No unmatched pet owners, orphaned vaccination/deworming records, missing timestamps, future user/pet birth dates, missing owner name/email, or unmatched authenticated-session user references were found.
- Both medical tables have a foreign key to `pets.id`, with cascade-on-delete. No pet deletion was executed.
- Pets have no `user_id` FK or Eloquent owner relationship. Owners are associated by mutable email. The applied controller safeguards protect current application flows, but cannot enforce integrity for direct database writes or all concurrent races.
- Owner fields are nullable in schema even though registration supplies them. All five existing pets have matching owners. No records were changed merely because a nullable field exists.
- Password hashes remain hidden in User serialization; forms do not populate password/hash fields. No plaintext-format stored password was detected; this is format inspection, not knowledge of existing users' passwords.

### Additional security observations

- Controller-level ownership checks cover pet detail, QR preview and QR PDF; lists scope by owner before loading medical records. Deliberate 403s were counted as passing protections.
- Public registration ignores submitted `role`; staff pet registration ignores forged owner metadata and selects the validated client server-side. Current controller create/update calls use validated/explicit field sets.
- Search uses bound query-builder parameters. No user-input SQL concatenation or unvalidated bulk assignment was found in application controllers.
- Blade escapes account/pet text. The feature-card raw icon input comes from application templates. Private QR output is generated by the QR library.
- Uploads require a validated image with JPG/JPEG/PNG/WebP MIME/extension and a 4 MB limit, and use generated storage filenames. Photos are on the public disk; authenticated record access does not protect a known photo URL. Confirm whether public pet photos match intended privacy requirements.
- Guest protected requests redirect to login. Missing-CSRF POST returns 419 with normal middleware enabled. Session cookies are HttpOnly and SameSite=Lax. Secure-cookie setting is false on this local HTTP installation.
- `APP_DEBUG` is enabled for the local environment. Before an Internet deployment, disable debug, use HTTPS/secure cookies, and serve only `public/`. Actual local HTTP probes returned 404 for `/.env` and `/bootstrap/audit-readonly.php`.
- Advisory checks: Composer reports no advisories or abandoned packages; npm reports 0 known vulnerabilities. Network-blocked attempts were retried with approved access. No dependencies were upgraded.
